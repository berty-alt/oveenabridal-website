# 13. RENTAL AVAILABILITY ENGINE

Availability is a critical business rule.

A dress variant is unavailable if an existing booking or maintenance block overlaps the requested period.

Use this overlap rule:

`requestedStart < existingEnd AND requestedEnd > existingStart`

Include configurable buffer days for:

* Cleaning
* Inspection
* Alterations
* Transport
* Preparation

Example:

If a dress is returned on 10 August and requires a two-day cleaning buffer, it must not be available before 13 August.

Prevent race conditions:

* Check availability on the server.
* Recheck availability during booking confirmation.
* Use database transactions.
* Add appropriate database-level locking or exclusion strategy.
* Never trust availability shown earlier in the browser.
* Provide idempotency protection where needed.

Write automated tests for:

* Exact date collision
* Partial overlap
* Booking contained within another booking
* Booking surrounding another booking
* Adjacent dates
* Cleaning buffer
* Cancelled booking
* Different dress variant
* Concurrent booking attempts

# 14. BOOKING WORKFLOW

Recommended workflow:

1. Customer chooses a dress.
2. Customer selects event and rental dates.
3. System checks availability.
4. Customer chooses fitting appointment.
5. Customer enters or selects measurements.
6. Customer reviews rental charges.
7. Customer accepts rental terms.
8. Customer sends a rental request.
9. Admin reviews the request.
10. Admin approves or proposes changes.
11. Customer pays the deposit.
12. Payment is verified server-side.
13. Booking becomes confirmed.
14. Dress dates are blocked.
15. Notifications are sent.
16. Staff performs fitting and alterations.
17. Dress is prepared for pickup.
18. Customer collects the dress.
19. Customer returns the dress.
20. Staff performs inspection.
21. Damage or cleaning charges are recorded.
22. Eligible deposit refund is processed.
23. Booking is completed.

Do not mark a booking confirmed based only on a frontend payment redirect. Verify the payment using the gateway’s server-side callback or API.

# 15. AI VIRTUAL TRY-ON

Implement AI Virtual Try-On only after the core catalogue and booking system are stable.

## Customer flow

1. Open a dress page.
2. Select “Try This Dress”.
3. Read photo requirements.
4. Accept explicit photo-processing consent.
5. Upload a full-body image.
6. Client validates type and basic size.
7. Server validates the file again.
8. Store it in private temporary storage.
9. Create a VirtualTryOnJob.
10. Send authorized input to the selected AI provider.
11. Process the request asynchronously.
12. Display progress safely.
13. Store the result temporarily.
14. Show the result with a clear AI disclaimer.
15. Allow download or deletion.
16. Automatically delete source and result files according to retention settings.

## Upload rules

Support only approved formats such as:

* JPEG
* PNG
* WebP

Perform:

* MIME verification
* File signature verification
* File size limit
* Pixel dimension limit
* Metadata removal
* Random storage names
* Malware scanning if available
* Image re-encoding
* Rate limiting
* Ownership checks

Do not trust the filename or browser-provided MIME type.

## AI disclaimer

Display:

“AI-generated preview only. Actual colour, fit, fabric drape, size and appearance may differ. Please book a physical fitting before confirming your rental.”

## Provider abstraction

Create an interface similar to:

* `createTryOnJob()`
* `getTryOnStatus()`
* `cancelTryOnJob()`
* `deleteTryOnAssets()`

Provide:

* Real provider implementation
* Mock provider implementation
* Error handling
* Retry policy
* Timeout
* Rate limiting
* Usage logging without storing unnecessary personal data

## Privacy

The system must record:

* Consent version
* Consent timestamp
* Purpose of processing
* Retention period
* Third-party processor
* Deletion status

Never use customer photos for model training unless the customer separately and explicitly opts in. The normal service must not depend on marketing or training consent.
